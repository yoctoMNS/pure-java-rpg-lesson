# 02. 制作ルール

この講座を作るときに、**必ず守る決まりごと**です。
台本を書く人・コードを書く人・動画を編集する人、全員がこれに従います。

---

## ルール0. この講座の2本の柱（最上位のルール）

> **受講者は「Javaは分かるが、ゲーム制作は初めて」の人です。**

だから、この講座には**2本の柱**があります。**どちらも削れません。**

| 柱 | 中身 | 扱い方 |
| --- | --- | --- |
| **①ゲームづくりの基礎** | ゲームループ・描画・タイルマップ・当たり判定・シーン・ターン制など | **知らない前提**。用語カードで手厚く説明する（ルール2） |
| **②オブジェクト指向の使いどころ** | 継承・ポリモーフィズム・抽象クラス・インターフェース・カプセル化 | **知っている前提**。定義ではなく「いつ使うか」だけを扱う（ルール1） |

### この2本は、別々の話ではありません

ゲームづくりで出てくる問題が、オブジェクト指向の道具をちょうど必要とします。

| 回 | ①ゲームの側から見ると | ②設計の側から見ると |
| --- | --- | --- |
| 7 | 主人公も町の人も「世界の中にいる物」 | だから共通の親（`Entity`）にまとめられる |
| 8 | 描画順を守って全員を描きたい | だから `List<Entity>` で1つのループにする |
| 17 | 画面ごとにまったく別のゲームになる | だから `Scene` という抽象クラスに分ける |
| 24 | 敵は確率の表から行動を選ぶ | だから行動をインターフェースで差しかえる |

**台本を書くときは、必ず①から入って②につなげます。** 逆にしてはいけません。
ゲームの問題を先に見せないと、設計の話がただの理屈になります。

### 迷ったときの選び方

| 迷ったとき | 選ぶほう |
| --- | --- |
| ゲームの**機能の量**を増やすか、説明を厚くするか | **説明**（モンスターやアイテムの数は、いくらでも減らせる） |
| 尺があふれた。何を削るか | **ゲームの機能の量**（①②の説明は削らない） |
| きれいなコードにするか、教えたい形にするか | **教えたい形**（ただし、なぜそうしたか言う） |
| 汎用的に作るか、いま必要な形で作るか | **いま必要な形**（作りすぎない。第15・21回で判断基準を示す） |

> **「ゲームの機能」と「ゲームづくりの考え方」は別物です。**
> モンスターを6種類から4種類に減らすのは、いつでもやってよい。
> 「なぜゲームループが必要か」の説明を削るのは、**絶対にやってはいけない**。

**「ゲームエンジンを作らない」というのは制約ではなく方針です。**
汎用の仕組みを作り始めると説明すべきことが増えすぎ、2本の柱がどちらもぼやけます。
使い回せる形にするのは、次シリーズ「2D RPG ゲームエンジン編」の仕事です。

## ルール1. オブジェクト指向の教え方（柱②）

### 1-1. 「先に困らせる」を必ず守る

**道具の説明から入ってはいけません。** 必ずこの順番にします。

1. **不便な書き方で、実際に書いてもらう**（動くコードにする。動かない例では困りが伝わらない）
2. **困る場面を、目の前で作る**（コピペした2ファイルを並べる／`switch` に枝を足す）
3. **問いかけて、3秒待つ**（「ここで速さの計算を直したくなったら、どうしますか？」）
4. **道具を出す**
5. **効き目を、その場で事実として見せる**（ルール1-3）

> **やってはいけない例**
> 「今日は継承をやります。継承とは、共通部分を親クラスにまとめることです」
> → これでは「へえ」で終わります。**困っていない人に道具を渡しても、ありがたみがありません。**

### 1-2. 「判断基準」を毎回1つ、言葉にして残す

受講者の本当の悩みは「道具を知らない」ことではなく、「**いつ使うか分からない**」ことです。
だから、毎回**持ち帰れる判断基準**を1つ、はっきり言葉にします。

| 回 | 言葉にする判断基準 |
| --- | --- |
| 第2回 | 中身を差しかえたいなら継承。使うだけなら継承しない |
| 第4回 | 1つのクラスには1つの仕事 |
| 第5回 | 状態を持たない道具は `static` でよい |
| 第6回 | `private` にするのは「守るべき決まりがある値」。getter/setter を全部作るのはカプセル化ではない |
| 第7回 | 「似ているから」ではなく「**同じ責任だから**」親に上げる |
| 第9回 | **「AはBの一種か」→ 継承。「AはBを持つか」→ コンポジション。迷ったらコンポジション** |
| 第13回 | その情報を**持っている**のは誰か。その判断は、その人の仕事 |
| 第15回 | **2回以上使うと分かっている物だけ**、部品にする |
| 第17回 | **状態を配りたいなら抽象クラス** |
| 第21回 | 1回しか使わない物は、専用に作ってよい |
| 第24回 | **約束だけなら インターフェース** |
| 第26回 | 同じ形の問題に見えても、**状態があるかどうかで答えが変わる** |

### 1-3. 「効き目」は、感想ではなく事実で見せる

道具を使ったあと、**必ず目の前で効果を確かめます。**

| ✕ 言ってはいけない | ○ こう見せる |
| --- | --- |
| 「きれいになりましたね」 | **`GamePanel` が82行 → 41行になりました**（画面に両方出す） |
| 「拡張しやすくなりました」 | **その場でNPCを5人に増やす。`add` を2行足すだけで動く** |
| 「保守性が上がります」 | **`Entity` を1行直す。`Player` と `Npc` が同時に直るのを見せる** |
| 「影響範囲が小さくなります」 | **`git diff GamePanel.java` を実行して、差分ゼロを見せる** |

**`git diff` を見せるのは、この講座でいちばん強い演出です。** 第19・27回で必ず使ってください。

### 1-4. 用語は使ってよい。ただし「知っている前提」で流さない

受講者は用語を習っています。だから**用語は普通に使います**（継承・ポリモーフィズム・カプセル化など）。

ただし、**「習ったけれど分かっていない」**のが前提です。用語を出したら、必ずセットにします。

```
【この回で使う道具】ポリモーフィズム
・ひとことで  : 親の型の箱に子を入れて、まとめて扱えること
・この場面では: List<Entity> に Player も Npc も入れて、1つのループで動かす
・効き目      : 新しい種類を足しても、このループは1行も変わらない
・判断基準    : 「同じ扱い方をしたい」ものが2種類以上あるとき
```

**「効き目」と「判断基準」の2つが、この講座で足す価値です。**
用語の定義だけなら、基礎講座でもう聞いています。

### 1-5. 抽象クラスとインターフェースは、必ず対で扱う

受講者がいちばん曖昧なまま終わっている論点です。**片方だけを教えてはいけません。**

- 第17回（抽象クラス `Scene`）で、**「なぜインターフェースではないか」**を言う
- 第24回（インターフェース `MonsterAction`）で、**「なぜ抽象クラスではないか」**を言う
- 第26回（抽象クラス `Item`）で、**受講者に自分で判断させる**（「今回もインターフェースでいいですか？」と問う）
- 第30回で、3つを並べた表でまとめる

**持ち帰ってほしい1文**：
> **状態を配りたいなら抽象クラス。約束だけなら インターフェース。**

## ルール2. ゲーム用語の教え方（柱①）

### 2-1. ゲームの用語は「知らない前提」で、必ず用語カードを出す

受講者はJavaを知っていますが、**ゲーム制作の言葉は1つも知りません。**
初出のときは、必ずこの形で説明します。**例外はありません。**

```
【用語カード】ゲームループ
・ひとことで : ゲームが動き続けるための、ぐるぐる回り続けるしくみ
・中身       : ①入力を見る ②世界を動かす（update） ③画面を描く（draw）
・なぜ必要か : ふつうのプログラムは上から下に処理して終わるが、
               ゲームは「終わらずに回り続ける」必要がある
・たとえ     : パラパラまんが。1枚描く → 少しずらす → また描く
```

- **「ひとことで」は40文字以内**
- **「なぜ必要か」を必ず入れる** ← ここがいちばん大事。
  仕組みだけ教えても、なぜそうするのかが分からなければ応用できません
- **「たとえ」は身のまわりの物で**（パラパラまんが・あなあきの紙・すごろく・くじ引きの箱）
- **可能なら実物・実演を見せる**（ルール2-3）

### 2-2. 手厚く説明するゲーム用語の一覧

`03_GLOSSARY.md` に全部載っています。**1つも省略しません。**

ゲームループ／FPS／update と draw／オフスクリーン描画／論理解像度／
押しっぱなしと押した瞬間／フォーカス／スプライト／スプライトシート／透過PNG／
ステータス／ゲームオブジェクト／描画順（Zオーダー）／更新順／
スプライトアニメーション／アニメ速度／デバッグ表示／
タイルマップ／マス座標とピクセル座標／レベルデザイン／データ駆動／
当たり判定／グリッド移動／カメラ／ワールド座標とスクリーン座標／カリング／
ゲームUI／等幅フォント／1文字ずつ表示／ページ送り／シーン／
イベントフラグ／かんたんスクリプト／エンカウント／フロントビュー／
敵パラメータ／元データとインスタンス／コマンドUI／ターン制／行動順／
ダメージ式／会心の一撃／ゲームバランス調整／成長曲線／
アイテムの種類／経済設計／セーブデータ設計／BGMとSE／音の形式

### 2-3. 「実演」を必ず1回入れる

ゲームの話は、**見せれば1秒で分かることが多い**です。言葉で説明せず、実演してください。

| 回 | 実演すること |
| --- | --- |
| 2 | 直接描く版を見せて、チラチラするのを体験してもらう |
| 2 | `RenderingHints` を入れる前と後を並べて、にじみの違いを見せる |
| 4 | 会話送りを「押しっぱなし」で作り、1回押しただけで飛ぶのを見せる |
| 5 | スプライトシートを画像ソフトで開き、1コマを赤枠で囲う |
| 8 | 描画順を逆にして、主人公が地面の下に隠れるのを見せる |
| 13 | 通れないマスに赤い枠を描く（見えない物を見えるようにする） |
| 14 | あなあきの紙を、大きな紙の上で実際に動かす |
| 15 | ひらがなだけの行と漢字混じりの行を並べ、幅の違いを見せる |
| 19 | 遭遇率を「3歩に1回」にして、うんざりするのを体験してもらう |
| 20 | コピーを作らないと、2回目に瀕死の敵が出るのを見せる |
| 23 | `DamageCalc` を1000回呼んで、ダメージの分布を数字で出す |
| 29 | MP3を入れて失敗するところを実演する |

### 2-4. 「どんなゲームでも同じ」と言えるものは、そう言う

受講者は**この講座のあとも、ゲームを作り続けます。**
だから、**この講座だけの話なのか、どこでも通じる話なのか**を、はっきり区別してあげます。

> 「ゲームループ・update と draw の分離・描画順・シーン——
> **これは Java だから、という話ではありません。**
> どのゲームエンジンを使っても、同じ言葉と同じ考え方が出てきます」

第30回のふりかえりで、この観点で一覧にします。

## ルール2b. 話しことば

### 使ってよい言葉のレベル

- **Java・オブジェクト指向の用語**はそのまま使います（受講者は習得済み）
- **ゲーム制作の用語**は、必ず用語カードを出してから使います（ルール2-1）
- **それ以外の言葉**は、できるだけやさしく書きます

> 第2版までは「中学校卒業までに習う言葉だけ」という制約でしたが、
> 対象者が「未経験者」から「Java基礎修了者」に変わったため緩めました。
> ただし、やさしく書くこと自体はやめません。

| 使ってよい | 使わない |
| --- | --- |
| 継承・ポリモーフィズム・カプセル化・抽象クラス・インターフェース | — |
| 四則演算・割合・確率・座標 | 三角関数・対数・ベクトル・行列・微分積分 |
| 「4回に1回くらい」「32歩に1回くらい」 | 「期待値」「標準偏差」 |

### むずかしい日本語は、やさしく言いかえる

| ダメな言葉 | 言いかえ |
| --- | --- |
| 汎用的な | いろいろな場面で使える |
| 冗長な | 同じことを何度も書いていて、むだが多い |
| 保守性が高い | あとから直しやすい |
| 疎結合 | おたがいのことを知らなくて済む |
| 凝集度が高い | 1つのクラスの中身が、1つの目的にそろっている |
| 適宜／随時 | そのときどきで／必要になったら |
| ～に起因する | ～が原因で |

**設計の用語（疎結合・凝集度・SOLID・パターン名）は、原則として使いません。**
第30回のまとめで1度だけ「これには名前があります」と紹介します。

### 効果を語るときは、必ず具体的に

| ✕ | ○ |
| --- | --- |
| 「変更に強くなります」 | 「**敵の行動を足しても、`BattleScene` を開かなくて済みます**」 |
| 「再利用性が上がります」 | 「**この `CommandMenu` は、このあと3回そのまま使います**」 |
| 「軽くなります」 | 「**1600マス描いていたのが、240マスになりました**」 |

## ルール3. 1本15分の作り方

### 3-1. 時間の割りふり（全回共通のテンプレート）

| 時間 | 中身 | 注意 |
| --- | --- | --- |
| 0:00 - 0:30 | **今日つくるもの**（動く画面を先に見せる） | |
| 0:30 - 1:00 | **前回のふりかえり** | 短く |
| 1:00 - 3:30 | ★**今日のゲームづくり** | **柱①**。用語カード＋実演（ルール2） |
| 3:30 - 4:30 | ★**今日のオブジェクト指向** | **柱②**。困る→道具（ルール1） |
| 4:30 - 11:00 | **いっしょに書く**（写経） | 3〜4個のかたまりに分け、その都度動かす |
| 11:00 - 12:30 | **一時停止チャレンジ** | 自分の頭で書く時間 |
| 12:30 - 13:30 | **効き目を確かめる** ＋ つまずきやすい所 | 事実で見せる（ルール1-3） |
| 13:30 - 14:30 | **まとめ（判断基準を1つ）＋ 宿題** | |
| 14:30 - 15:00 | **次回予告** | 山場の前は「次回、困ってもらいます」と予告 |

**ゲームづくりの説明に2分30秒**、**オブジェクト指向に1分**——これが基本の配分です。
受講者はゲーム制作が初めてなので、①のほうが厚くなります。

**山場の回（第7・17・24・26・28回）だけ、配分を変えます。**

| 時間 | 中身 |
| --- | --- |
| 0:00 - 0:30 | 今日つくるもの |
| 0:30 - 2:00 | ★**今日のゲームづくり**（用語カード。ここで「なぜ困るか」の下地を作る） |
| 2:00 - 3:30 | **困らせる**（不便な書き方を実際に書き、問いかけて3秒待つ） |
| 3:30 - 5:30 | ★**今日のオブジェクト指向**（判断基準の表をしっかり見せる） |
| 5:30 - 11:00 | いっしょに書く |
| 11:00 - 12:30 | 一時停止チャレンジ |
| 12:30 - 13:30 | **効き目を確かめる**（`git diff` や行数比較） |
| 13:30 - 15:00 | まとめ ／ 次回予告 |

**山場の回でも、ゲームづくりの説明を省きません。**
たとえば第17回なら「シーンという考え方」を先に教えてから、`switch` の破綻を見せます。
**ゲームの問題が先、設計の解決があと**——この順番は絶対です。

### 3-2. 「かたまりごとに動かす」

8分の写経を、いっきに書かせてはいけません。
**「10〜20行書く → すぐ動かす → 動いた」を3〜4回くり返します。**

とくに**書き直しの回（第7・17・24・26回）は、1つ移すたびに動かします。**
「動いていた物が動かなくなる」時間を、できるだけ短くするためです。

### 3-3. 一時停止チャレンジ（必須）

**毎回、1分30秒とります。** 尺があふれても、1分までしか縮めません。

- 「ここで動画を止めて、自分で書いてみてください」と言い、**課題文を出したまま10秒待つ**
- 課題は**その回で習ったことだけ**で解ける物にする
- 大きさは **5〜15行**
- **山場の回では、「道具を使う側」の課題にする**
  （例：第7回「`Entity` を継承して、動かないNPCを作ってください」）
  → 道具を使うと簡単に書けることを、自分の手で確かめてもらうため

### 3-4. まとめでは「判断基準」を必ず1つ言う

- ✕「今日は継承をやりました」
- ○「**今日から、親に上げるかどうかは『同じ責任か』で決めてください。** 似ているだけでは上げません」

計画書（`01_COURSE_PLAN.md`）の各回の「今日のオブジェクト指向」に書いた判断基準を、そのまま言ってください。

### 3-5. 画面の作り（動画編集のルール）

| 項目 | 決まり |
| --- | --- |
| 動画の大きさ | 1920 × 1080 |
| コードの文字の大きさ | **20pt 以上** |
| 今書いている行 | 黄色い枠で囲む |
| **2つのファイルを比べるとき** | **必ず左右に並べ、同じ行に色をつける**（第7回など） |
| **行数の変化を見せるとき** | **前と後を並べて、数字を大きく出す**（第17回など） |
| **`git diff` を見せるとき** | ターミナルを大きく映す（第19・27回） |
| 字幕 | 全編に付ける |
| チャプター | 3-1 の8つの区切りで付ける |
| 早送り | 写経部分は早送りしない |

## ルール4. コードの書き方のルール

### 4-1. 量の制限

| 回 | 新しく書くコードの上限 |
| --- | --- |
| 第1〜10回 | **40行** |
| 第11〜20回 | **50行** |
| 第21〜30回 | **55行** |

**第3版より各回5行ずつ下げました。**「今日のゲームづくり」に2分30秒を使うため、
写経に使える時間が6分30秒に減ったからです。

上限の合計は1,450行、**実際の見積もりは約1,230行**です（`06_ARCHITECTURE.md`）。

**書き直しの回では、「移す行数」は上限に数えません**（新しく書く行だけ数えます）。

### 4-2. 名前の付け方

| 対象 | 決まり | 例 |
| --- | --- | --- |
| クラス | 英語・大文字はじまり | `Player`, `TileMap`, `BattleScene` |
| 変数・メソッド | 英語・小文字はじまり | `worldX`, `canWalk()` |
| 定数 | 英語・全部大文字 | `TILE_SIZE` |
| コメント | **日本語** | `// マップ全体での位置` |

**座標の名前は必ず区別します**（第14回）：`worldX` / `screenX`。
意味の違う数字に同じ名前を使わないこと自体が、設計の一部です。

### 4-3. 使ってよい書き方・使わない書き方

| 使う | 使わない（この講座では最後まで出しません） |
| --- | --- |
| クラス・継承・抽象クラス・インターフェース | ジェネリクスの自作（`<T>`）— **次シリーズで扱います** |
| `enum`・`switch` | ラムダ式・ストリーム |
| `ArrayList`・`HashMap`・`List`/`Map` 型で受ける | `record`・`sealed` |
| `static`（状態を持たない道具と定数） | 匿名クラス・内部クラス |
| `try`/`catch` | 例外の自作・`finally`・try-with-resources |
| `@Override`（**必ず付ける**） | `Thread`・`Runnable`（`Timer` を使う） |
| `var` を使わない（型を明示する） | デザインパターン名を出すこと |

> **`@Override` は必ず付けます。** 飾りではなく、名前を間違えたときに
> コンパイルエラーで気づける道具だからです（第10回で扱います）。

> **デザインパターンの名前は出しません。** 第24回の `MonsterAction` は
> Strategy パターンそのものですが、名前は言いません。
> **判断できることが目的で、名前を覚えることは目的ではない**からです。
> 第30回のまとめで、「これには名前が付いています」と1度だけ触れます。

### 4-4. 書き直し（リファクタリング）について

**この講座では、書き直しを意図的に入れます。**

- 第7回（`Entity` に共通部分を上げる）

未経験者向けなら避けるべきですが、**この講座では書き直しの体験そのものが教材**です。
ただし、次を必ず守ってください。
