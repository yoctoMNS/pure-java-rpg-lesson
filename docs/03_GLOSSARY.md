# 1. ゲーム制作の用語（★手厚く説明する）

**1つも省略しません。** 初出のときは、必ず用語カードを出します（`02_RULES.md` ルール2-1）。

## 1-1. ゲームの動くしくみ（第1〜4回）

### ゲームプログラムの形 — 第1回
- **ひとことで**: 「準備」→「ぐるぐる回り続ける」→「終わり」の3つに分かれている
- **ふつうのプログラムとの違い**: ふつうは上から下に処理して終わる。ゲームは終わらずに回り続ける
- **なぜ必要か**: プレイヤーがいつ何を押すか分からないので、ずっと待ち構えている必要がある
- **大事な点**: キャラが止まって見えるときも、裏では1秒60回、同じ処理が回っている

### ゲームループ — 第3回
- **ひとことで**: ゲームが動き続けるための、ぐるぐる回り続けるしくみ
- **中身**: ①入力を見る ②世界を動かす（update） ③画面を描く（draw）
- **たとえ**: パラパラまんが。1枚描く → 少しずらす → また描く
- **どんなゲームでも同じ**: エンジンが変わっても、この形は変わりません

### update と draw を分ける — 第3回 ★最重要
- **update**: 世界の状態を変える（位置を動かす、HPを減らす）
- **draw**: いまの状態を絵にする。**状態は変えない**
- **なぜ分けるか**: 混ぜると「描くたびに位置が動く」ようになり、原因が追えなくなる
- **この講座では**: 30回ずっと守ります

### FPS（フレーム毎秒） — 第3回
- **ひとことで**: 1秒間に画面を描きかえる回数
- **この講座では**: 60FPS。1回ぶんは 1000ミリ秒 ÷ 60 ＝ 約16ミリ秒
- **なぜ60か**: 多くの画面が1秒に60回書きかわるから。それ以上描いても見えない

### オフスクリーン描画（下書きに描く） — 第2回
- **ひとことで**: 画面に直接描かず、いったん「見えない紙」に全部描いてから、まとめて貼る
- **なぜ必要か**: 直接描くと、描いている途中が見えてチラチラする
- **たとえ**: 黒板に直接書くのではなく、紙に書いてから黒板に貼る

### 論理解像度 — 第2回
- **ひとことで**: ゲームの中での画面の大きさ。実際のウィンドウの大きさとは別に決める
- **この講座では**: ゲームの中は 256×240、ウィンドウは 768×720（3倍）
- **なぜ必要か**: ①ドット絵が大きくくっきり見える ②座標の計算が小さい数字で済む
- **注意**: ふつうに拡大するとにじむ。「なめらかにしない」設定が必要

### 押しっぱなし と 押した瞬間 — 第4回 ★つまずく人が多い
- **押しっぱなし**: 押されている「間ずっと」反応する。**移動**に使う
- **押した瞬間**: 押された「その1回だけ」反応する。**決定・メニュー選択**に使う
- **なぜ区別が必要か**: 会話の「次へ」を押しっぱなし判定にすると、1回押しただけで最後まで飛ぶ（1秒60回反応するため）
- **作り方**: 「いま押されている ＆ さっきは押されていなかった」で判定する

### フォーカス — 第4回
- **ひとことで**: いま、どの部分がキー入力を受け取るか
- **注意**: `setFocusable(true)` を忘れると、キーがまったくきかない

## 1-2. 絵とキャラクター（第5〜10回）

### スプライト — 第5回
- **ひとことで**: ゲームの中で動き回る、キャラクターや物の絵
- **この講座では**: 16×16 ピクセル

### スプライトシート（キャラクターチップ） — 第5回
- **ひとことで**: たくさんの絵を、1枚の画像にまとめた物
- **なぜまとめるか**: ①ファイルを何十個も読むより速い ②管理しやすい
- **たとえ**: 着せかえシールのシート
- **使い方**: 「この位置の、この大きさ」を指定して切り出す

### 透過PNG — 第5回
- **ひとことで**: 背景が「なし」になっている画像
- **なぜ必要か**: 背景が白いままだと、キャラの周りに白い四角が出る
- **確かめ方**: 画像ソフトで開き、背景が市松模様なら透過されている

### ステータス（パラメータ） — 第6回
- **ひとことで**: キャラクターの強さや状態を表す数字のまとまり
- **RPGの基本**: HP／MP／ちから／みのまもり／すばやさ
- **大事な点**: どの数字にも「守るべき決まり」がある（HPは0未満にならない等）
- **バグの元**: ゲームのバグの多くは、この決まりが破れたときに起きる

### ゲームオブジェクト（エンティティ） — 第7回
- **ひとことで**: ゲームの世界の中にいる「物」。主人公・町の人・敵・宝箱など
- **共通しているもの**: 位置がある／向きがある／毎フレーム動く／毎フレーム描かれる
- **大事な点**: 見た目や役わりが違っても、「世界の中にいる物」としては同じ扱いができる

### 描画順（Zオーダー） — 第8回
- **ひとことで**: 「あとから描いた物が、上に重なる」という決まり
- **なぜ大事か**: 順番を間違えると、主人公が地面の下に隠れたりする
- **RPGの基本の順**: ①マップ → ②キャラクター → ③ウィンドウ・文字
- **たとえ**: 画用紙に絵の具を重ねるのと同じ

### 更新順 — 第8回
- **ひとことで**: 誰から先に動かすか
- **注意点**: 主人公を先に動かすと、NPCは「主人公はもう新しい位置にいる」状態で判断する
- **この講座では**: 主人公 → NPC の順に固定（分かりやすさ優先）

### スプライトアニメーション — 第9回
- **ひとことで**: 何枚かの絵を順番に見せて、動いているように見せること
- **1枚1枚**: 「コマ」（フレーム）と呼ぶ
- **この講座では**: 4方向 × 2コマ ＝ 8枚

### アニメ速度 — 第9回
- **ひとことで**: 何フレームごとにコマを切りかえるか
- **速すぎると**: 足がバタバタして見える／**遅すぎると**: カクカクして見える
- **この講座では**: 10フレームごと（1秒に6回）
- **調整のコツ**: 「歩く速さ」と「足の速さ」が合っていないと、滑って見える

### デバッグ表示 — 第10回
- **ひとことで**: ふだんは見えない情報を、開発中だけ画面に出すこと
- **よく出す物**: FPS／座標／いまのマス／当たり判定の枠／いまのシーン
- **なぜ必要か**: ゲームは「見た目」でしか結果が分からない。数字を出さないと何が起きているか分からない
- **鉄則**: **見えない物は、見えるようにしてから直す**
- **配る前に**: 必ずオフにする

## 1-3. マップ（第11〜14回）

### タイルマップ — 第11回
- **ひとことで**: マップを、同じ大きさの四角い絵（タイル）を敷きつめて作るしくみ
- **データの持ち方**: 「どのマスに、何番のタイルを置くか」という数字の表
- **なぜタイルか**: ①絵が少しで済む ②数字で作れるので速い ③通れるかをタイル番号で判断できる
- **たとえ**: フロアタイル

### マス座標 と ピクセル座標 — 第11回
- **マス座標**: 左から何マス目・上から何マス目（col, row）
- **ピクセル座標**: 画面の中の位置（x, y）
- **変換**: `x = col × 16`、`col = x ÷ 16`
- **注意**: 混ぜるとバグになる。名前で必ず区別する

### レベルデザイン — 第12回
- **ひとことで**: マップの形や敵の配置を考えて作る仕事
- **ゲーム制作では**: プログラムを書く仕事とは別の、独立した仕事として扱われる
- **なぜ分けるか**: マップ1枚直すたびにプログラムを書きかえていたら、何百枚も作れない

### データ駆動 — 第12回
- **ひとことで**: ゲームの中身を、プログラムではなく外部のファイルで決めること
- **良い点**: ①プログラマ以外でも作れる ②直すたびに動かし直さなくていい
- **この講座では**: マップ・タイルの性質・会話・モンスター・成長表・アイテムの6つ

### 当たり判定（コリジョン） — 第13回
- **ひとことで**: 「ぶつかっているか」「そこへ行けるか」を調べること
- **2つのやり方**: ①四角どうしが重なっているか（アクション向き） ②そのマスに入れるか（RPG向き。この講座）
- **大事な点**: 動かしてから調べるのではなく、**動く前に「行き先」を調べる**（先読み判定）

### グリッド移動（マス目移動） — 第13回
- **ひとことで**: 1マスぶんきっちり動く移動のしかた
- **作り方**: ①行き先を決める ②通れるなら「移動中」にする ③着くまで少しずつ近づける ④解除
- **大事な点**: 移動中は次のキーを受けつけない（受けると壁をすり抜ける）
- **なぜRPGはこれか**: 「どのマスの前に立っているか」の判定が簡単になる
- **たとえ**: すごろく

### カメラ — 第14回
- **ひとことで**: 広いマップの、どこを映すかを決める「窓」
- **たとえ**: 大きな絵を、あなあきの紙ごしに見る
- **作り方**: カメラの位置を持ち、描くときに引き算で画面での位置に直す

### ワールド座標 と スクリーン座標 — 第14回
- **ワールド座標**: マップ全体での位置／**スクリーン座標**: 画面の中での位置
- **変換**: `スクリーン座標 ＝ ワールド座標 − カメラの位置`
- **注意**: この2つを混ぜるのが、スクロール系のバグの原因のほぼすべて

### カリング — 第14回
- **ひとことで**: 画面に映らない物は描かない、という工夫
- **効果**: この講座では 1600マス → 240マス
- **ゲーム制作の基本**: 「見えない物を描くのは、時間のむだ」

## 1-4. 画面と会話（第15〜18回）

### ゲームUI — 第15回
- **ひとことで**: 会話まど・コマンド・持ち物など、プレイヤーに情報を見せる部分
- **ふつうのアプリとの違い**: 部品を使わず、すべて自分で「描いて」作る
- **なぜ自分で描くか**: ①ゲームの見た目に合わせられる ②どの環境でも同じに見える

### 等幅フォント と 文字の折り返し — 第15回
- **等幅フォント**: どの文字も同じ幅のフォント
- **なぜ使うか**: 1行に何文字入るかが「数えるだけ」で分かる
- **漢字を使わない理由**: ひらがな・カタカナだけなら幅がそろう

### 1文字ずつ表示（タイプライター表示） — 第16回
- **ひとことで**: 文章をいっきに出さず、1文字ずつ増やして見せること
- **作り方**: 「いま何文字目まで出すか」の数を毎フレーム増やす
- **なぜやるか**: ①読むテンポが生まれる ②RPGらしい雰囲気
- **親切設計**: 全部出る前に決定キーを押したら、すぐ全部出す

### ページ送りと入力待ち — 第16回
- **ひとことで**: 1画面ぶん出したら、決定キーが押されるまで待つこと
- **「▼」の点滅**: 「まだ続きがあります」の合図
- **大事な点**: ここで「押した瞬間」判定が必要（第4回の仕込み）

### シーン（ゲームステート） — 第17回 ★最重要
- **ひとことで**: タイトル・マップ・戦闘・店など、「画面ごとにまったく別のゲーム」と考えること
- **なぜそう考えるか**: 画面が違えば、動かす物も描く物も操作方法も全部違う
  （マップでは十字キーで歩き、戦闘では十字キーでカーソルを動かす）
- **持ち方**: 「いまどのシーンか」を1つだけ持ち、そのシーンだけを動かす／描く
- **どんなゲームでも同じ**: 市販のエンジンにも必ずこの仕組みがある

### イベントフラグ — 第18回
- **ひとことで**: 「もうやったか、まだか」を覚えておく印
- **RPGでの例**: 王様と話した／カギを手に入れた／ボスを倒した
- **たとえ**: ラジオ体操カードのハンコ
- **注意**: 増えると管理が大変。名前を決めておく（`KING_TALKED` のように）

### かんたんスクリプト — 第18回
- **ひとことで**: ゲームの中の出来事を、台本ファイルで書くこと
- **この講座の形**: 「誰が」「どのフラグが立っているとき」「何を話すか」を1行で
- **良い点**: セリフを直すのにプログラムを触らなくていい

## 1-5. 戦闘（第19〜24回）

### エンカウント — 第19回
- **ひとことで**: 歩いているときに敵と出会うこと
- **2つの方式**: ①シンボルエンカウント（敵が見えている） ②ランダムエンカウント（この講座）
- **調整のコツ**: 「32歩に1回くらい」が目安。多すぎるとストレス、少なすぎると退屈
- **親切設計**: 戦闘直後はしばらく出さない（連戦を防ぐ）

### フロントビュー — 第19回
- **ひとことで**: 自分の姿は映らず、敵だけが正面に見える戦闘の見せ方
- **良い点**: 味方の絵を描かなくていい／画面がシンプル
- **もう一方**: サイドビュー（横から見て、味方も敵も見える）

### 敵パラメータの設計 — 第20回
- **持たせる物**: HP／MP／ちから／みのまもり／すばやさ／経験値／ゴールド／絵
- **考え方**: 「序盤の敵は2〜3発で倒せる」「もらえる経験値は手間に見合う」
- **調整の順番**: ①適当な数字で動かす ②戦ってみる ③直す（最初から完璧な数字は決められない）

### 元データとインスタンス — 第20回
- **ひとことで**: 「スライムという種類」と「いま戦っているスライム1体」は別物
- **なぜ分けるか**: 元データのHPを直接減らすと、次のスライムが瀕死で出てくる
- **作り方**: 戦うたびに、元データからコピーを作る
- **ゲーム制作の基本**: この「型とコピー」は、アイテムでも弾でも同じ

### コマンドUI — 第21回
- **ひとことで**: プレイヤーが行動を選ぶための、一覧つきの画面
- **部品**: ①選択肢の一覧 ②カーソル（▶） ③決定キーとキャンセルキー
- **カーソルの動かし方**: 「選んでいる番号」を1つの数字で持つ。2列なら `番号 ÷ 2` で行、`番号 % 2` で列
- **親切設計**: 端で反対側に回りこむ／カーソルを点滅させる

### ターン制 — 第22回
- **ひとことで**: 全員が1回ずつ行動したら1ターン、というルールで進む戦闘
- **1ターンの流れ**: ①コマンドを選ぶ ②行動順を決める ③順番に行動 ④勝敗を確かめる ⑤①へ
- **大事な点**: 「入力待ち」があちこちに入る

### 行動順 — 第22回
- **単純な決め方**: すばやさが高い順
- **この講座の決め方**: `すばやさ ＋ 0〜(すばやさ−1)のでたらめな数` で点数を出し、高いほうが先
- **なぜ乱数を混ぜるか**: 「速いほうが有利。でもたまに逆転する」気持ちよさ。毎回同じだと飽きる

### ダメージ式 — 第23回
- **この講座の式**:
  ```
  もとのダメージ = こうげき力 − しゅび力 ÷ 2
  実際のダメージ = もとのダメージ × (75〜125 のでたらめな数) ÷ 100
  1 より小さくなったら 1
  ```
- **なぜ「÷2」か**: 守備をそのまま引くと、守備が高い敵に一切ダメージが通らない
- **なぜ乱数の幅（±25%）か**: 毎回同じ数字だと機械的で、戦っている感じがしない
- **なぜ最低1か**: 「絶対に倒せない敵」を作らないため（詰みを防ぐ）

### 会心の一撃 — 第23回
- **ひとことで**: まれに出る、相手の守りを無視する強い攻撃
- **この講座では**: 32回に1回くらい
- **なぜ入れるか**: たまに起きる「うれしい出来事」が、戦闘の退屈さを減らす

### ゲームバランス調整 — 第23回
- **ひとことで**: 数字を変えて、ちょうどよい難しさにする作業
- **やり方**: ①戦ってみる ②「強すぎる／弱すぎる」を感じる ③数字を直す
- **プロのコツ**: 計算部分だけを取り出して何百回も走らせる（手で戦うよりはるかに速い）

### 敵AI — 第24回
- **ひとことで**: 敵が次に何をするかを決めるしくみ
- **RPGでよくある方式**: 「確率の表」から1つ選ぶだけ（とても単純）
- **なぜ単純でよいか**: 賢すぎる敵はプレイヤーを苛立たせる。「たまに変なことをする」くらいが楽しい

### 確率テーブル — 第24回
- **ひとことで**: 「行動」と「その割合」を並べた表
- **例**: たたかう60／じゅもん20／ぼうぎょ15／なにもしない5
- **引き方**: 1〜100の乱数を引き、上から順に引き算していく
- **たとえ**: くじ引きの箱。100本のうち60本が「たたかう」

## 1-6. 育てる・仕上げる（第25〜30回）

### 成長曲線 — 第25回
- **ひとことで**: レベルが上がるにつれて、強さや必要経験値がどう増えていくかの形
- **よくある形**: 必要経験値はだんだん増えていく（0 → 5 → 15 → 30 → 55 …）
- **なぜ増やすか**: 同じペースだと、後半がすぐレベルアップして手ごたえがなくなる

### 計算式か、表か — 第25回
- **計算式**: 作るのは楽／**表**: 調整が自由
- **この講座では**: 表。「レベル5だけ少し強く」といった調整ができるから
- **ゲーム制作では**: 表のほうが一般的。数字はゲームの手ざわりそのもの

### アイテムの種類と効果 — 第26回
- **種類**: どうぐ（使うとなくなる）／ぶき・よろい（装備する）／たいせつなもの（使えない）
- **共通する物**: 名前・値段・説明文／**違う物**: 使ったときに何が起きるか
- **持ち物の上限**: 上限があると「何を持つか選ぶ」楽しさが生まれる

### ゲームの経済設計 — 第27回
- **ひとことで**: ゴールドが「どれだけ手に入り、何に使えるか」の設計
- **考え方**: 「敵を10体倒したら、次の武器が買えるくらい」が目安
- **値段の決め方**: ①その武器でどれだけ楽になるか ②貯めるのに何体倒すか ③手間に見合うか

### 装備の計算 — 第27回
- **式**: `こうげき力 = ちから ＋ 武器の強さ` ／ `しゅび力 = みのまもり ＋ 防具の強さ`
- **コツ**: 装備するたびに足すのではなく、**毎回その場で計算する**
- **なぜか**: 装備を外したときの引き算を忘れるバグが、構造的に起きなくなる

### セーブデータ設計 — 第28回
- **ひとことで**: 「何を保存すれば、続きから遊べるか」を決めること
- **保存する物**: 位置・レベル・経験値・所持金・持ち物・装備・フラグ
- **保存しない物**: 計算で出せる物（こうげき力）／一時的な物（いまのシーン、アニメのコマ）
- **見分け方**: 「ゲームを閉じて開いたとき、これがないと困るか？」
- **保存場所**: ユーザーのホームフォルダ（ゲームのフォルダは書けないことがある）

### BGM と SE（効果音） — 第29回
- **BGM**: ずっと流れ続ける音楽。シーンごとに変える
- **SE**: 一瞬だけ鳴る音。決定・カーソル・攻撃・回復・レベルアップ
- **BGMの注意**: ①ループさせる ②シーンを変えるときは前のを必ず止める（二重に鳴る）
- **SEの注意**: 鳴らすたびに読むと遅れる。最初に全部読んでおく

### Javaで鳴らせる音の形式 — 第29回
- **鳴らせる**: WAV / AIFF / AU ／ **鳴らせない**: MP3 ← つまずく人がいちばん多い
- **BGMの長さ**: 30〜60秒くらいのループ用の短い曲（WAVはファイルが大きい）

### ゲームを配る — 第30回
- **jar**: プログラムと素材を1つにまとめたファイル
- **クレジット**: 使った素材の作者名を書いて同梱する。CC0でも書くのが礼儀
- **配る前に**: デバッグ表示をオフにする

# 2. オブジェクト指向の道具（定義は載せない）

受講者は定義を知っています。書くのは**「使いどころ」「効き目」「判断基準」**だけです。

### 継承（extends）
| | |
| --- | --- |
| **借りる側** | 第2回 `GamePanel extends JPanel`。描く中身を自分の物に差しかえる |
| **作る側** | 第7回 `Entity`。`Player` と `Npc` の共通部分を上げる |
| **効き目** | `Entity` を1行直すと `Player` と `Npc` が同時に直る |
| **判断基準** | 「似ているから」ではなく「**同じ責任だから**」上げる |
| **使わない判断** | 第2回 `JFrame`（中身を差しかえたいわけではない）／第20回 `Monster`（マップの上を動かない） |

### ポリモーフィズム
| | |
| --- | --- |
| **場面** | 第8回 `List<Entity>` に `Player` も `Npc` も入れ、1つのループで動かす |
| **効き目** | **新しい種類を足しても、ループは1行も変わらない** |
| **判断基準** | 「同じ扱い方をしたい」ものが2種類以上あるとき |
| **登場回** | 8, 17, 19, 24, 26, 27（6回） |

### カプセル化
| | |
| --- | --- |
| **場面** | 第6回 HPを `private` にして `damage()` / `heal()` を用意 |
| **効き目** | 第28回でセーブを書くとき、**状態が2か所に集まっている**ので55行で済む |
| **判断基準** | **その値に守るべき決まりがあるか**（HPにはある。座標にはない） |
| **よくある誤解** | 「`private` ＋ getter/setter を全部作る」のはカプセル化ではない |
| **登場回** | 6, 13, 18, 28（4回） |

### 抽象クラス
| | |
| --- | --- |
| **場面** | 第17回 `Scene`／第26回 `Item` |
| **効き目** | 第19回 `BattleScene` を足しても `GamePanel` の差分がゼロ |
| **判断基準** | **共通の「状態」があるなら抽象クラス** |
| **登場回** | 17, 26（2回。24回のインターフェースと必ず対で扱う） |

### インターフェース
| | |
| --- | --- |
| **使う側** | 第3回 `ActionListener`／第4回 `KeyListener`。「呼んでもらうための札」 |
| **作る側** | 第24回 `MonsterAction`。敵の行動を差しかえられるようにする |
| **効き目** | 新しい行動を足しても `BattleScene` は1行も変わらない |
| **判断基準** | **共通の状態がなく、振る舞いの約束だけなら インターフェース** |
| **登場回** | 3, 4, 24, 29（4回） |

### コンポジション（has-a）
| | |
| --- | --- |
| **場面** | 第9回 `Entity` が `Sprite` を持つ |
| **効き目** | `Entity` の仕事が「マップの上での動き」だけに保たれる |
| **判断基準** | 「AはBの**一種**か？」→継承／「AはBを**持つ**か？」→コンポジション。**迷ったらコンポジション** |
| **登場回** | 9, 20, 27（3回） |

### 単一責任（1クラス1つの仕事）
| | |
| --- | --- |
| **場面** | 第4回 `KeyHandler`／第5回 `ImageLoader`／第23回 `DamageCalc`／第29回 `SoundManager` |
| **効き目** | 第23回：`DamageCalc` を切り出したので、**ゲームを起動せずにバランス調整ができる** |
| **判断基準** | そのクラスの説明に「と」が入ったら、分けどきかもしれない |
| **登場回** | 4, 5, 23, 29（4回） |

### すべての道具に共通する効き目
第30回のまとめで、この1文に集約します。各回でも、この言い方に寄せてください。

> **「何かを足したいとき、既にあるコードを開かなくて済む」**

そして、持ち帰ってほしい1文：

> **状態を配りたいなら抽象クラス。約束だけなら インターフェース。**

# 3. わざと出さない言葉

現場では使いますが、**この講座では出しません**。（**第30回のまとめでだけ**1度触れます）

| 出さない言葉 | この講座での言い方 |
| --- | --- |
| Strategy パターン | 行動を差しかえられるようにする（第24回） |
| Template Method パターン | 流れは親が決め、中身は子が書く（第17回） |
| SOLID・単一責任の原則 | 1つのクラスには1つの仕事 |
| 開放閉鎖の原則 | 足すときに、既にあるコードを開かなくて済む |
| 疎結合 | おたがいのことを知らなくて済む |
| 凝集度 | 1つのクラスの中身が、1つの目的にそろっている |
| 委譲 | 別のクラスに、その仕事をまかせる |
| DI・依存性注入 | 使う物を、外から渡してもらう |
| ゲームエンジン／フレームワーク | （**作らない**。次シリーズで扱う） |
| ジェネリクス（自作） | （**使わない**。次シリーズで扱う） |
| スレッド・マルチスレッド | （**使わない**。`Timer` で作る） |
| デルタタイム | （**使わない**。60FPS固定） |
| ダブルバッファリング | 下書きに描いてから、まとめて貼る（第2回） |
| ビット演算 | （**使わない**） |

**なぜ名前を出さないか**：
名前を覚えても、**いつ使うかは判断できるようになりません。**
この講座の目的は判断できるようになることです。名前は、判断できたあとで知れば十分です。
