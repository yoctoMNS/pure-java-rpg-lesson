# 03. 用語集

受講者は Java の基礎を終えているので、**文法用語の定義は載せません。**
このファイルに載せるのは次の2つだけです。

1. **オブジェクト指向の道具**を、この講座ではどう説明するか（定義ではなく**使いどころ**）
2. **ゲーム特有の用語**（受講者が初めて出会うもの）

**動画では、必ずここに書いた言い方で説明します。** 回ごとに言い方を変えてはいけません。

## 1. オブジェクト指向の道具

定義は書きません。**「この講座では、どの場面で、なぜ使うか」**だけを書きます。

### 継承（extends）

| | |
| --- | --- |
| ひとことで | 他人が用意した流れの中に、自分の処理を割りこませる／共通の責任を親にまとめる |
| **借りる側** | 第2回 `GamePanel extends JPanel`。`paintComponent` を差しかえて、描く中身を自分の物にする |
| **作る側** | 第7回 `Entity`。`Player` と `Npc` の共通部分を上げる |
| **効き目** | 直す場所が1か所になる。`Entity` を1行直すと `Player` と `Npc` が同時に直る |
| **判断基準** | 「似ているから」ではなく「**同じ責任だから**」上げる |
| **使わない判断** | 第2回 `JFrame` は継承しない（中身を差しかえたいわけではない）／第20回 `Monster` は `Entity` を継承しない（マップの上を動かない） |

### ポリモーフィズム

| | |
| --- | --- |
| ひとことで | 親の型の箱に子を入れて、まとめて扱えること |
| 主な場面 | 第8回 `List<Entity>` に `Player` も `Npc` も入れ、1つのループで動かす |
| **効き目** | **新しい種類を足しても、ループは1行も変わらない** |
| 判断基準 | 「同じ扱い方をしたい」ものが2種類以上あるとき |
| 出てくる回 | 8, 17, 19, 24, 26, 27（**6回**） |

### カプセル化

| | |
| --- | --- |
| ひとことで | 守るべき決まりのある値を、外から直接いじれないようにすること |
| 主な場面 | 第6回 HPを `private` にして `damage()` / `heal()` を用意する |
| **効き目** | 第28回でセーブを書くとき、**状態が2か所に集まっている**ので60行で済む |
| 判断基準 | **その値に守るべき決まりがあるか**（HPは0未満・最大超過がダメ → 守る。座標に決まりはない → そのままでよい） |
| **よくある誤解** | 「`private` ＋ getter/setter を全部作る」のはカプセル化ではない。`setHp(-50)` が通るなら `public` と同じ |
| 出てくる回 | 6, 13, 18, 28（**4回**） |

### 抽象クラス（abstract class）

| | |
| --- | --- |
| ひとことで | 共通の状態と処理を配りつつ、中身の一部を子に書かせるしくみ |
| 主な場面 | 第17回 `Scene`（画面）／第26回 `Item`（アイテム） |
| **効き目** | 第19回 `BattleScene` を足しても `GamePanel` の差分がゼロ |
| **判断基準** | **共通の「状態」があるなら抽象クラス** |
| 出てくる回 | 17, 26（**2回**。24回のインターフェースと必ず対で扱う） |

### インターフェース（interface）

| | |
| --- | --- |
| ひとことで | 「これができます」という約束だけを決めるもの |
| **使う側** | 第3回 `ActionListener`／第4回 `KeyListener`。「呼んでもらうための札」 |
| **作る側** | 第24回 `MonsterAction`。敵の行動を差しかえられるようにする |
| **効き目** | 新しい行動を足しても `BattleScene` は1行も変わらない |
| **判断基準** | **共通の状態がなく、振る舞いの約束だけなら インターフェース** |
| 出てくる回 | 3, 4, 24, 29（**4回**） |

### コンポジション（has-a）

| | |
| --- | --- |
| ひとことで | 継承するのではなく、「持つ」こと |
| 主な場面 | 第9回 `Entity` が `Sprite` を持つ |
| **効き目** | `Entity` の仕事が「マップの上での動き」だけに保たれる |
| **判断基準** | 「AはBの**一種**か？」→ 継承／「AはBを**持つ**か？」→ コンポジション。**迷ったらコンポジション** |
| 出てくる回 | 9, 20, 27（**3回**） |

### 単一責任（1クラス1つの仕事）

| | |
| --- | --- |
| ひとことで | 1つのクラスには、1つの仕事だけをさせる |
| 主な場面 | 第4回 `KeyHandler`／第5回 `ImageLoader`／第23回 `DamageCalc`／第29回 `SoundManager` |
| **効き目** | 第23回：`DamageCalc` を切り出したので、**ゲームを起動せずにバランス調整ができる** |
| 判断基準 | そのクラスの説明に「と」が入ったら、分けどきかもしれない |
| 出てくる回 | 4, 5, 23, 29（**4回**） |

### この講座の言い方の統一（重要）

**すべての道具に共通する効き目は、1つの文にまとめます。**

> **「何かを足したいとき、既にあるコードを開かなくて済む」**

第30回のまとめで、この1文に集約します。各回でも、この言い方に寄せてください。

## 3. 「わざと出さない言葉」の一覧

現場では使いますが、**この講座では出しません**。かわりの言い方を使います。
（**第30回のまとめでだけ**、「これには名前があります」と1度触れます）

| 出さない言葉 | この講座での言い方 |
| --- | --- |
| Strategy パターン | 行動を差しかえられるようにする（第24回） |
| Template Method パターン | 流れは親が決め、中身は子が書く（第17回） |
| SOLID・単一責任の原則 | 1つのクラスには1つの仕事 |
| 開放閉鎖の原則 | 足すときに、既にあるコードを開かなくて済む |
| 疎結合 | おたがいのことを知らなくて済む |
| 凝集度 | 1つのクラスの中身が、1つの目的にそろっている |
| 委譲 | 別のクラスに、その仕事をまかせる |
| DI・依存性注入 | 使う物を、外から渡してもらう |
| リファクタリング | コードの整理・引っ越し |
| ジェネリクス（自作） | （**使わない**。次シリーズで扱う） |
| デザインパターン全般 | （**名前は出さない**。形だけ使う） |
| スレッド・マルチスレッド | （**使わない**。`Timer` で作る） |
| ビット演算 | （**使わない**。セーブは今どきの方式なので不要） |

**なぜ名前を出さないか**：
名前を覚えても、**いつ使うかは判断できるようになりません。**
この講座の目的は判断できるようになることです。名前は、判断できたあとで知れば十分です。
